# 플러그인·Microkernel: 확장점과 신뢰 경계를 따로 설계하기

문서 0.1.0 · 검토 2026-09-19 · 도구·제품군·장치 확장 구조

## 개념과 특징

애플리케이션 수준의 microkernel/plugin 구조는 작은 공통 핵심이 확장 계약을 제공하고 제품별 기능을 플러그인으로 연결한다. 운영체제의 microkernel 설계와는 다른 사용 문맥이다. 플러그인 로딩은 보안 sandbox나 프로세스 격리를 자동 제공하지 않는다.

[Python Packaging의 공식 플러그인 안내](https://packaging.python.org/en/latest/guides/creating-and-discovering-plugins/)는 이름 규칙·namespace·package metadata를 이용한 발견 방법을 설명한다. 이것은 확장 발견의 예이지 임의 패키지를 안전하게 실행할 수 있다는 보증이 아니다. [OWASP 위협 모델링](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html)의 경계 분석을 함께 적용한다.

## 구조와 동작

```text
호스트: 설정·수명주기·자원 제한·공개 계약
  ├─ 프로토콜 확장 A
  ├─ 보고서 확장 B
  └─ 저장 형식 확장 C
발견 → 승인/호환 검사 → 초기화 → 사용 → 중단 → 자원 해제
```

신뢰할 수 없는 확장은 별도 프로세스·권한·통신 계약으로 격리하는 방안을 검토한다. 서명이 있다고 안전한 동작이 보장되는 것은 아니며 서명은 출처·무결성 확인의 한 요소다.

## 구현 순서

1. 실제로 여러 구현이 필요한 지점을 고른다. 추측성 확장점으로 핵심 API를 복잡하게 만들지 않는다.
2. 플러그인 ID·API 판본·필요 기능·설정 schema·자원 사용·수명주기를 계약으로 정의한다.
3. 허용 목록과 설치/업데이트 검토 경로를 두고 발견과 활성화를 분리한다. 검색 결과를 바로 import/실행하지 않는다.
4. 초기화의 부분 실패를 역순 정리하고 중복 ID·의존 순환·호환되지 않는 버전을 거부한다.
5. 종료 시 신규 호출을 막고 진행 작업·콜백을 정리한 뒤 코드/자원을 해제한다. 동적 unload가 필요 없으면 종료 시까지 유지하는 방식이 더 단순할 수 있다.

## 장점과 비용

제품별 변형과 확장 책임을 분리하고 핵심 릴리즈와 일부 기능의 변경 주기를 나눌 수 있다. 반면 API 호환, 설치 신뢰, 의존성 충돌, 장애·자원 관리 비용이 생긴다. in-process 플러그인의 crash나 메모리 손상은 호스트까지 영향을 줄 수 있다.

## 적용·비추천 조건

편집기·분석 도구·프로토콜 변환기·여러 고객용 제품 변형에 적합하다. 구현이 한 개이고 외부 확장이 없거나 정적 검증·메모리 예측이 핵심인 작은 MCU는 빌드 시 선택하는 정적 어댑터가 나을 수 있다. 런타임 로딩을 재사용성의 필수 조건으로 생각하지 않는다.

## 검증과 전환

계약 시험 묶음을 모든 플러그인에 동일 적용한다. 잘못된 판본·악성 설정·느린 응답·초기화 실패·종료 후 콜백을 검사한다. 기존 변형의 공통 부분을 확인한 뒤 한 확장점만 분리하고, 호스트의 내부 객체를 ABI로 노출하지 않는다.

## 근거와 한계

2026-09-19 열람한 변동 문서와 독자 구성안이다. 실제 플러그인을 설치·실행하거나 새 확장 권한을 부여하지 않았다. 언어 ABI·프로세스 sandbox·MCU 실기는 not_tested다. [Ports & Adapters](/guides/hexagonal_clean)는 이 구조와 함께 사용할 수 있다.
