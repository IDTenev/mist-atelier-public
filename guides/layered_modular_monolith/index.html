계층형과 모듈러 모놀리스: 하나로 배포하되 경계는 지키기

문서 0.1.0 · 검토 2026-09-19 · 서버·데스크톱·펌웨어 구성 가이드

개념과 특징

계층은 UI·업무 규칙·저장/장치 접근처럼 책임을 나눈다. 모듈러 모놀리스는 업무 기능별 모듈이 한 배포 단위 안에서 공개 계약으로 협력하는 구조다. 둘은 경쟁 관계가 아니다. 모듈 내부에 필요한 계층을 둘 수 있다. 소스 저장소 하나와 프로세스 하나, 배포 하나도 항상 같은 의미는 아니다.

Microsoft N-tier 문서 ↗는 논리적 계층과 물리적 계층을 구분한다. Spring Modulith ↗는 모듈 공개 API와 내부 구현 접근을 나누는 실제 도구의 예다. 아래 구조는 특정 Java 프레임워크를 설치하라는 지시가 아닌 독자적 적용안이다.

구조와 동작

app / composition_root
  ├─ acquisition / public_api / internal
  ├─ catalog     / public_api / internal
  ├─ reporting   / public_api / internal
  └─ adapters   / database, serial, files
입력 → 기능 모듈의 공개 API → 규칙 검사 → 저장/장치 어댑터 → 결과

폴더만 나누고 다른 모듈의 내부 객체·테이블을 임의 수정하면 경계가 없다. 모듈이 자기 상태를 소유하고 다른 모듈은 명시한 명령·조회로 접근한다. common에는 실제 공유되는 안정적인 값만 넣고 모든 업무 객체를 모으지 않는다.

구현 순서

  1. 변경 이유가 같은 기능을 묶는다. 화면별·테이블별 분리보다 사용 사례와 소유 데이터를 먼저 적는다.
  2. 각 모듈의 공개 입력/출력, 오류 코드, 트랜잭션 범위를 정한다. 내부 저장 타입을 그대로 외부에 노출하지 않는다.
  3. 프로그램 시작부에서 의존성을 조립한다. 모듈 초기화 순서와 실패 시 역순 정리도 구현한다.
  4. import/include 의존성 검사로 내부 접근과 순환 참조를 막는다. C에서는 공개 헤더와 내부 헤더를 구분하고 빌드 대상의 include 경로를 제한한다.
  5. 실제 저장소·드라이버와 통합 시험을 추가한다. 한 프로세스라도 스레드·ISR이 공유 상태에 접근하면 동기화가 필요하다.

장점과 비용

단일 배포·디버깅 경로를 유지하고 함수 호출로 협력하므로 시작과 통합 시험이 비교적 단순하다. 로컬 트랜잭션을 활용하기도 쉽다. 반면 전체를 함께 배포하며 프로세스 장애·메모리 누수의 영향도 공유한다. 특정 모듈만 다른 비율로 확장하는 데 한계가 있다. 계층마다 값만 전달하는 래퍼를 만들면 코드만 늘어난다.

적용·비추천 조건

업무 경계가 바뀌는 초기 제품, 운영 인력이 적은 서비스, 장비 제어 프로그램, 하나의 펌웨어에 적합한 출발점이다. 반대로 규제/권한상 강한 격리나 실제 독립 배포·별도 자원 확장이 필요하면 프로세스·서비스 분리를 검토한다. Fowler의 Monolith First ↗는 경험 기반 논지이지 모든 조직에 적용되는 정리나 통계적 보증이 아니다.

검증과 전환

공개 API 계약 시험, 순환 의존성 0건, 모듈별 소유 데이터 쓰기 경로, 초기화 실패 정리를 확인한다. 한 모듈 장애가 전체에 미치는 영향도 시험한다. 분리할 때는 먼저 API 경계와 데이터 소유권을 안정화한 뒤 낮은 결합의 기능 한 개를 외부로 옮긴다. 함수 호출을 원격 호출로 치환하는 것만으로는 충분하지 않다. 서비스 분리의 타임아웃·중복·버전 계약이 추가된다.

근거와 한계

링크는 2026-09-19 열람한 변동 웹 문서다. 개념을 비교했으며 Spring/클라우드 설치나 언어별 빌드는 수행하지 않았다. 디렉터리와 도입 절차는 독자 작성한 설계 예시이고 실행 코드가 아니다. MCU 실기·독립 서비스 전환의 성능은 not_tested다.
