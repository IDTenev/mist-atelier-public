# DDD와 기능 경계: 데이터 이름보다 의미와 소유자를 나누기

문서 0.1.0 · 검토 2026-09-19 · 업무·장비 도메인 설계

## 개념과 특징

DDD는 업무 개념과 규칙을 코드 모델에 맞추는 접근이다. [Bounded Context 해설](https://martinfowler.com/bliki/BoundedContext.html)은 큰 모델을 의미가 일관된 문맥으로 나누고 문맥 사이 관계를 명시한다. 같은 ‘장치’라도 설치 관리의 자산, 통신의 주소, 계측의 데이터 생산자는 다른 모델일 수 있다.

Bounded Context는 반드시 프로세스나 마이크로서비스 한 개가 아니다. 먼저 [모듈러 모놀리스](/guides/layered_modular_monolith) 안의 경계로 구현할 수 있다. [Spring Modulith의 모듈 경계](https://docs.spring.io/spring-modulith/reference/fundamentals.html)는 공개 API와 내부 타입의 접근 통제를 지원하는 구체 사례이며, DDD 전체를 자동으로 완성하는 도구는 아니다.

## 구조와 동작

```text
자산 관리: asset_id, 설치 위치, 정비 상태
      ↓ 명시적 식별자/상태 변환
장치 통신: endpoint_id, 연결 세대, protocol_version
      ↓ 측정 이벤트 계약
계측 관리: measurement_id, 단위, 품질, 측정 시각
```

한 문맥의 내부 객체를 다른 문맥이 직접 수정하지 않는다. 서로 다른 용어·단위를 경계 어댑터에서 변환한다. 모든 문맥을 만족하는 거대한 공통 `Device` 객체를 만드는 것은 피한다.

## 구현 순서

1. 운영자·개발자가 주요 명령과 사실을 나열한다. ‘측정 시작 요청’과 ‘측정 완료’를 구분한다.
2. 항상 함께 지켜야 할 규칙을 모은다. 예를 들어 한 실행 ID의 상태 전이와 결과 확정은 같은 소유자가 처리하도록 한다.
3. 핵심 규칙이 붙은 상태 묶음과 트랜잭션 경계를 정한다. 여러 문맥을 가로지르는 원자성이 필요한지 먼저 질문한다.
4. 공개 계약에 식별자, 단위, 판본, 오류, 중복 규칙을 넣고 소유자와 변경 승인자를 정한다.
5. 모듈 단위로 구현한 뒤 실제 변경 빈도·팀 소유권·운영 요구가 분리를 정당화할 때만 원격 경계로 옮긴다.

## 장점과 비용

용어 충돌과 규칙의 중복 구현을 줄이고 변경 담당을 명확히 한다. 반면 도메인 대화와 모델 조정 시간이 필요하며 문맥 사이 변환 코드가 생긴다. 모든 CRUD에 복잡한 엔티티·리포지터리 계층을 강제하면 단순 작업이 느려진다. 데이터를 나누는 이익보다 빈번한 교차 조회 비용이 클 수도 있다.

## 적용·비추천 조건

장비 수명주기·정비·통신·계측처럼 같은 단어의 의미가 달라지고 팀별 규칙이 다른 시스템에 적합하다. 단일 표를 읽어 보여 주는 도구나 도메인 규칙이 거의 없는 변환기는 가벼운 함수·모듈 구성이 먼저다. 조직도만 보고 서비스를 나누지 않는다.

## 검증과 전환

대표 시나리오를 실제 업무 용어로 시험한다. 다른 문맥의 저장소에 직접 쓰는 경로, 동시 상태 변경, 오래된 판본 메시지, 누락된 식별자 변환을 확인한다. 경계가 잘못됐으면 분산 배포 전에 모듈을 합치거나 옮긴다. 외부 시스템 모델이 핵심 모델을 오염시키면 변환 계층을 추가하되 단순 이름 변경 래퍼는 만들지 않는다.

## 근거와 한계

2026-09-19 열람한 공개 웹 문서를 개념 근거로 사용했다. 장비 문맥·도입 순서는 독자적 설계 예시다. DDD는 보편적인 폴더 규격이 아니며 위 경계가 실제 조직에 맞는지는 도메인 검토가 필요하다. 제품 통합·실기 상태는 not_tested다.
