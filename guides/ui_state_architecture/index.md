# MVC·MVVM·단방향 상태: 화면과 업무 로직을 분리하기

문서 0.1.0 · 검토 2026-09-19 · 웹·데스크톱·장비 HMI

## 개념과 특징

MVC는 모델·뷰·입력 조정 책임, MVVM은 화면을 위한 상태/명령과 바인딩 경계, 단방향 데이터 흐름은 입력에 따른 상태 변경과 렌더링 방향에 초점을 둔다. 프레임워크별 의미가 다르므로 이름만 같다고 동일 구현으로 취급하지 않는다.

[Qt Model/View 문서](https://doc.qt.io/qt-6/model-view-programming.html)는 모델·뷰·delegate 협력을 설명한다. [React 상태 구조 안내](https://react.dev/learn/choosing-the-state-structure)는 모순·중복·불필요한 상태를 줄이도록 한다. [Microsoft MVVM](https://learn.microsoft.com/en-us/dotnet/architecture/maui/mvvm)은 View와 ViewModel의 역할을 설명한다. 아래 HMI 구성은 이 개념을 비교한 독자적 제안이다.

## 구조와 동작

```text
사용자 입력 → command/action → 사용 사례 → 장치/서버
                     ↓ 진행/결과/오류
                화면 상태 소유자 → 렌더링
관측 값과 사용자가 편집 중인 값은 구분
```

화면의 ‘버튼 활성화’는 편의 기능이며 서버/장치의 권한·안전 검사를 대신하지 않는다. 응답이 늦게 와도 이전 요청 결과가 최신 선택 화면을 덮지 않게 요청 세대를 확인한다.

## 구현 순서

1. 영속 업무 상태, 서버에서 읽은 상태, 편집 중인 임시 상태, 표시용 파생값을 구분한다.
2. `loading/success/error`처럼 동시에 성립하면 안 되는 상태는 하나의 명시 상태로 표현한다.
3. 명령은 UI 이벤트에서 사용 사례로 전달하고 장치/네트워크 호출은 어댑터로 분리한다. UI 스레드에서 긴 블로킹 I/O를 실행하지 않는다.
4. 취소·재시도·중복 클릭·화면 이탈·응답 역순 정책을 구현한다. 취소 UI가 실제 서버 작업의 취소 완료를 뜻하는지 구분한다.
5. 키보드, 초점, 오류 안내, 연결 끊김, 오래된 관측값의 표시를 인수 기준에 넣는다.

## 장점과 비용

업무 시험과 화면 시험을 분리하고 여러 화면에서 규칙을 공유하기 쉽다. 반면 상태 동기화·바인딩·action 흐름이 늘 수 있다. 모든 필드를 전역 store에 올리면 수명과 갱신 범위가 불명확해진다. 단순 화면은 지역 상태로 시작한다.

## 적용·비추천 조건

장비 상태·편집 폼·장시간 작업을 함께 보여주는 HMI, 여러 뷰가 같은 모델을 보는 도구에 유리하다. 정적 문서 페이지나 단일 표시 위젯에 복잡한 전역 상태 프레임워크를 도입할 필요는 없다. 현장 알람의 신뢰 판단을 애니메이션이나 색상 하나에 의존하지 않는다.

## 검증과 전환

응답 순서를 바꾸고 화면을 닫은 뒤 완료를 전달해 본다. 오류와 stale 상태가 접근 가능한 텍스트로 드러나는지, 새로고침 시 편집 데이터가 어떻게 되는지 확인한다. 가장 복잡한 화면 한 개부터 사용 사례·화면 상태를 분리한다. [상태 머신](/guides/state_machine_active_object)과 [Ports & Adapters](/guides/hexagonal_clean)를 조합할 수 있다.

## 근거와 한계
