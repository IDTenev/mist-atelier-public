독립 재생·파생 뷰 · 원본은 하나, 시점과 표현은 여러 개

검토: 2026-09-20 · 분류: 구현 패턴 / 한 소스·다중 뷰 / 범용 연속 데이터 설계

별칭: Replay View, Materialized View, Read Model, Timeline Cursor

적용 분야: 계측 파형·표·통계, 실시간/과거 로그 비교, 블랙박스 재생, 동기/비동기 멀티뷰

개념과 특징

논리 원본을 보존하고 뷰는 이를 읽어 만든 표현으로 다룬다. 단순 동시 렌더링이면 같은 immutable snapshot을 여러 UI가 읽으면 된다. 각 화면의 시간창·재생 속도·필터가 달라지면 독립 cursor/상태가 필요하다. 지속 조회 비용이 크면 별도 materialized view를 만들지만 작은 앱에 CQRS 서버를 강제하지 않는다.

구조와 동작

확정 원본 로그 → 뷰별 cursor/변환 상태 → 파형 / 표 / 집계 / 재생 화면

뷰 상태는 source_id, epoch, position, clock mapping, filter, transform_version, view_generation으로 식별한다. 원본 수정 명령은 별도 owner로 보내며 읽기 뷰가 공유 데이터를 직접 변경하지 않는다.

언제 쓰고 피할까

  • 사용: 하나의 센서/로그를 다른 시간창·해상도·표현으로 보여주거나 화면을 멈춰도 기록은 계속해야 하는 경우. 계산 결과를 다시 생성할 수 있어야 할 때.
  • 비추천: 동일 상태를 똑같이 두 번 보여줄 뿐인데 별도 DB와 이벤트 처리 서버를 추가하는 경우. 원본이 이미 삭제됐는데 임의 과거 시점의 완전 재생을 요구하는 경우.

장점과 비용

  • 장점: 표시 로직과 수집을 분리하고 새로운 뷰를 원본에서 재계산할 수 있다. 원본 ID와 변환 버전으로 결과를 추적한다.
  • 단점·비용: 뷰마다 처리 상태·인덱스·캐시가 필요하고 지연된 뷰는 서로 다른 시점을 나타낼 수 있다. 저장 기간 밖 재생은 불가능하며 파생 결과만으로 원본 복원이 안 될 수 있다.

설계·구현 가이드

  1. 같은 현재값의 여러 표현인지, 독립 seek/속도인지, 서버에 저장할 파생 모델인지 구분해 가장 작은 구조를 고른다.
  2. 뷰별 position과 원본의 committed_high_watermark를 노출한다. 사용자는 실시간·일시정지·지연·보존 범위 밖을 구분할 수 있어야 한다.
  3. seek는 새 view_generation에서 시작하고 오래된 비동기 decode/계산 결과는 폐기한다. 동일 시각으로 묶은 뷰는 공통 재생 clock을 쓰되 허용 skew를 명시한다.
  4. 필터/보정/집계 버전을 기록하고 전체 구간 재계산 또는 dual-run 후 새 뷰를 게시한다. 변환 중간 결과를 완성본으로 바꾸지 않는다. 삭제/권한 정책은 원본뿐 아니라 캐시·파생 뷰에도 전달한다.

적용 예시

하나의 진동 스트림에서 원시 파형, RMS 통계, 이벤트 목록을 보여준다. 원시 파형은 5초 되감고 RMS는 실시간이어도 각각 position을 표시하면 혼동하지 않는다. 두 영상 창이 같은 frame을 crop하는 경우에는 decode 결과를 공유할 수 있지만 서로 다른 시점이면 독립 decoder 상태 또는 재사용 가능한 decode cache가 필요하다.

이 절은 독자 작성 설계 사례이며 실행 프로그램이나 바로 적용할 운영 설정 파일이 아니다.

실패·동시성·종료 조건

모든 뷰가 같은 mutable “현재 위치”를 바꾸면 한 화면의 seek가 다른 화면을 끊는다. 파생 view가 뒤처졌다는 이유로 원본을 최신 결과에 맞춰 덮지 않는다. 종료 시 읽기 lease·decode surface·worker를 뷰 단위로 반환한다. 화면 crop은 서버 권한 분리를 대신하지 않는다.

검증 기준

같은 원본 구간·변환 버전에서 뷰를 두 번 재생해 결과가 같은지 검사한다. 한 뷰 seek/정지/종료 중 나머지 기록·뷰의 cursor가 바뀌지 않아야 한다. 보존 만료, 필터 변경, generation 교체와 동기 뷰 skew 상한도 확인한다.
