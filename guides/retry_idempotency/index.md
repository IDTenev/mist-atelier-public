# 재시도·멱등성 · 응답 유실과 중복 실행 분리

검토: 2026-09-20 · 분류: 구현 패턴 / 통신·프로토콜 / 오류 회복 패턴

별칭: Retry, Backoff, Jitter, Idempotency, Deduplication, ACK

적용 분야: 장치 명령, HTTP API, 작업 소비자, 메시지 전송

## 개념과 특징

timeout은 원격 실행 실패를 뜻하지 않는다. 재시도는 같은 논리 작업을 다시 시도하고, 멱등성은 반복이 업무 효과를 중복시키지 않는 계약이다. ACK도 접수·저장·실행 완료 중 어떤 의미인지 정해야 한다.

## 구조와 동작

작업 ID 생성 → 전송 → 응답/timeout → 재시도 가능 여부·남은 예산 검사 → 같은 ID 재전송 → 기존 결과 또는 단일 실행

## 언제 쓰고 피할까

- 사용: 일시 장애가 있고 동일 작업 재시도의 안전성을 서비스 또는 장치가 보장할 수 있을 때.
- 비추천: 인증 오류·잘못된 입력·영구 고장, 중복 제어 동작이 위험한데 중복 제거 장치가 없는 경우.

## 장점과 비용

- 장점: 일시적인 통신 장애를 견딘다. 논리 ID와 결과 기록이 있으면 응답 유실 후 결과 조회가 가능하다.
- 단점·비용: 부하와 최악 지연이 증가한다. 여러 계층의 재시도는 시도 횟수를 곱하고, dedup 기록 보관 기간·정합성 비용이 든다.

## 설계·구현 가이드

1. 재시도 가능한 오류를 allowlist로 나누고 전체 deadline·최대 시도·최대 지연을 둔다. SDK 자체 재시도와 겹치지 않게 소유 계층 하나를 정한다.
2. 동일 논리 작업에는 같은 ID와 동일 payload를 사용한다. ID 재사용 시 payload가 다르면 거절한다.
3. 수신 측 dedup 기록과 업무 변경을 가능한 같은 transaction에 묶는다. 처리 중·성공·실패 상태와 보관 기간을 정의한다.
4. 지수 backoff의 상한을 두고 지연을 분산한다. 만료·취소 후에는 새 재시도를 시작하지 않는다.

## 적용 예시

“목표 위치 100으로 설정”과 “100만큼 이동”은 중복 효과가 다르다. 이동이 완료됐으나 ACK만 유실되면 후자를 무조건 재전송하지 말고 command_id 결과를 조회한다.

이 절은 구현 결정을 설명하는 설계 사례다. 실행 프로그램이나 장비 설정 파일이 아니다.

## 실패·동시성·종료 조건

메모리 dedup은 재부팅하면 사라진다. 기록 만료 이후 같은 ID도 새 실행이 될 수 있으므로 무기한 exactly-once를 주장하지 않는다. 결과 불명 상태를 단순 실패로 덮지 않는다.

## 검증 기준

실행 직후 응답 유실·동시 같은 ID·동일 ID 다른 payload·기록 만료·재부팅·취소 중 backoff를 시험한다. 수락된 한 논리 작업의 업무 효과가 계약대로 한 번이어야 한다.
