장애 격리와 복원력: 타임아웃·재시도·Circuit Breaker·Bulkhead

문서 버전: 0.1.0 · 검토: 2026-09-19 · 검증 상태: not_tested

개념과 특징

타임아웃은 기다림의 한도, 재시도는 다시 실행하는 정책, Circuit Breaker는 실패가 누적된 의존성 호출을 잠시 차단하는 상태, Bulkhead는 자원 풀을 분리하여 장애 확산을 제한하는 구조입니다. 각각 다른 문제를 풀며 추가할수록 좋은 장식이 아닙니다.

구조와 동작

요청 + 전체 마감
  → 업무별 동시성/큐 한도 (Bulkhead)
  → 의존성 상태 검사 (Circuit Breaker)
  → 남은 기한 안의 호출 + 제한된 재시도
  → 정상 결과 / 명시된 대체 결과 / 실패

Breaker는 닫힘(호출 허용), 열림(빠른 거절), 제한된 시험 호출 상태를 가질 수 있습니다. 라이브러리별 집계 창·상태 이름·시험 동시성은 다릅니다. 호출 차단은 이미 실행 중인 원격 작업의 취소나 취소 완료 확인을 뜻하지 않습니다.

구현 순서

  1. 사용자 관점의 전체 기한과 각 의존성 예산을 먼저 정합니다. 단계마다 새로 전체 시간을 주면 총 응답 시간이 늘어납니다.
  2. 재시도 가능한 오류와 불가능한 오류를 구분합니다. 읽기도 고비용 요청이면 예산이 필요하고, 쓰기는 중복 적용 방지 계약 없이는 자동 재전송하지 않습니다.
  3. 재시도 책임을 한 계층에 두고 최대 시도 수·총 시간·최대 지연·무작위 분산(jitter)을 정합니다. 여러 계층의 재시도 곱셈을 피합니다.
  4. 중요 업무와 배치 업무의 작업자·연결·큐 예산을 분리합니다. 공통 DB가 병목이면 애플리케이션 풀만 나눠도 충분하지 않습니다.
  5. Breaker가 계산할 실패 종류·최소 표본·집계 창·차단 시간·시험 호출 수를 설정합니다. 권한 오류를 서비스 전체 장애로 잘못 세지 않습니다.
  6. 대체 값이 가능한 경우 신선도·출처·누락을 응답에 표시합니다. 안전 제어에 오래된 값을 정상값처럼 반환하지 않습니다.

예를 들어 화면 조회에 총 800 ms가 허용된다는 가상의 요구에서는 인증·로컬 처리·원격 호출·응답 여유를 합쳐 그 안에 들어가게 배분합니다. 이 숫자는 추천 기본값이 아닙니다. 실제 지연 분포와 업무 요구에서 정해야 합니다.

장점과 비용

  • 장점: 실패를 빨리 알리고 중요 작업의 자원을 보호합니다. 일시 장애의 회복 가능성과 무한 재시도를 구분할 수 있습니다.
  • 비용: 상태와 임계값이 늘고 잘못된 설정은 멀쩡한 요청도 차단합니다. 업무별 풀은 유휴 자원을 공유하지 못해 효율이 떨어질 수 있습니다.
  • 한계: 연결 취소·시간 초과 뒤에도 원격 부작용은 남을 수 있습니다. 재시도 성공이 중복 부작용 없음을 증명하지 않습니다.

적용·비추천 조건

추천: 느려지는 외부 API가 전체 스레드·연결을 고갈시키는 서비스, 서로 다른 중요도의 작업이 자원을 공유하는 시스템. 비추천: 측정 없이 모든 로컬 함수 호출에 Breaker를 씌우는 구조. 하드웨어 비상 정지·안전 제어는 별도 안전 요구와 검증이 필요하며 일반 서비스 패턴으로 인증을 대체할 수 없습니다.

검증과 전환

정상·고지연·연결 실패·부분 성공·지속 과부하·의존성 복구를 각각 시험합니다. 시험 호출 폭주, 종료 후 늦은 응답, 큐 포화, 취소 미지원 라이브러리도 포함합니다. 전체 마감 초과율, 거절 사유, 실제 원격 시도 수, 진행 중 작업 수, 자원 회수 시간을 측정합니다. 타임아웃·유한 큐부터 도입하고 관측된 실패에 맞춰 격리와 차단을 추가합니다.

근거와 한계

  • Microsoft: Circuit Breaker ↗ — 차단·회복 시험 상태와 적용 조건.
  • Microsoft: Bulkhead ↗ — 자원 분할과 장애 격리 비용.
  • Google SRE: Handling Overload ↗ — 과부하 시 제한·부하 차단·재시도 예산을 고려하는 근거.
