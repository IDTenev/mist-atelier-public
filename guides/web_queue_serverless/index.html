Web-Queue-Worker와 Serverless: 오래 걸리는 일을 요청에서 분리하기

문서 버전: 0.1.0 · 검토: 2026-09-19 · 검증 상태: not_tested

개념과 특징

Web-Queue-Worker는 요청을 받는 부분, 대기열, 실제 작업자를 나누는 처리 구조입니다. Serverless는 서버 관리의 일부를 플랫폼에 맡기는 실행·운영 방식입니다. 같은 개념이 아니며, 큐 작업자는 장기 실행 프로세스나 관리형 함수 모두로 구현할 수 있습니다.

보고서 생성·사진 변환처럼 즉시 끝나지 않는 작업에 적합합니다. 함수 실행 시간·메모리·동시성 제한은 제공자·계정·설정에 따라 확인해야 합니다. 짧은 함수라는 이유로 실시간 마감이 보장되지는 않습니다.

구조와 동작

클라이언트 → 접수 API → 작업 레코드 + 발행 의도 저장
                         ↓ relay → 유한 큐 → 작업자 → 결과 저장
클라이언트 → 상태 조회 API ← 접수/실행/성공/실패/취소 상태

HTTP 202와 작업 ID는 접수 계약이지 완료 보장이 아닙니다. DB에 접수된 직후 큐 발행이 실패하는 구간은 Outbox 또는 플랫폼이 제공하는 확인된 원자성 계약으로 다룹니다. 큐와 DB가 알아서 함께 커밋된다고 가정하지 않습니다.

구현 순서

  1. 입력 크기·권한·작업 비용 한도와 완료 목표 시간을 정합니다. 큰 파일은 승인된 저장소 참조로 전달하고 접근 권한을 검증합니다.
  2. 중복 접수 키, 작업 ID, 입력 판본, 요청자, 만료 시각을 기록합니다. 같은 키에 다른 입력을 보내면 충돌로 반환합니다.
  3. 내구성 있는 접수와 발행 의도를 저장한 뒤 응답합니다. 큐 가시성 시간·lease·재전달 정책을 문서화합니다.
  4. 작업자는 결과 저장과 완료 처리를 멱등하게 구성합니다. 재시작 이후 이미 적용된 부작용을 조회할 수 있어야 합니다.
  5. 최대 동시 작업 수를 DB 연결·메모리·외부 API 예산 이하로 제한합니다. 계정의 함수 동시성 한도가 업무별 격리를 대신하지는 않습니다.
  6. 영구 오류는 실패 상태 또는 격리 큐로 옮기고, 일시 오류만 횟수·전체 기한을 제한하여 재시도합니다. 취소 요청과 이미 완료된 외부 부작용을 구분합니다.

함수 인스턴스 재사용은 연결 초기화 비용을 줄일 수 있지만, 메모리·임시 디스크를 유일한 작업 상태로 삼으면 안 됩니다. 요청별 사용자 데이터가 재사용 인스턴스에 남지 않도록 수명을 관리합니다.

장점과 비용

  • 장점: 요청 응답과 긴 작업을 분리하고 작업자만 확장할 수 있습니다. 큐가 짧은 유입 급증을 흡수할 수 있습니다.
  • 비용: 상태 조회 UI, 중복 처리, 취소·재처리·격리 운영이 필요합니다. 큐는 무한 용량이 아니며 지속 과부하를 해결하지 못합니다.
  • Serverless의 비용: 사용량 기반 실행이 유리할 수도 있지만 초기화 지연, 외부 연결 수, 호출·저장·전송 요금과 관측 비용을 함께 측정해야 합니다. 항상 싸다는 결론은 내리지 않습니다.

적용·비추천 조건

추천: 결과를 나중에 받아도 되는 변환·인덱싱·알림·보고서 작업. 비추천: 정해진 수십 마이크로초 안에 반응해야 하는 제어 루프, 장기 연결 상태를 함수 메모리에만 유지하는 설계. 단순하고 짧은 DB 조회라면 동기 API부터 시작합니다.

검증과 전환

같은 작업의 중복 전달, 완료 저장 직후 ACK 유실, lease 만료 중 기존 작업자 생존, 큐 적체·만료, 취소와 완료의 경쟁을 시험합니다. 처리율·가장 오래 기다린 작업의 나이·실패율·격리 건수·작업당 비용을 기록합니다. 저위험 작업 하나부터 분리하고 기존 처리로 돌아갈 때도 이중 실행을 막는 권한 전환점을 둡니다.

근거와 한계

  • Microsoft: Web-Queue-Worker ↗ — 웹 요청과 백그라운드 작업을 나누는 구조의 근거.
  • AWS Lambda best practices ↗ — 실행 환경 재사용, 멱등성, 동시성·자원 제약 확인의 근거.

2026-09-19 확인한 문헌을 바탕으로 작성한 설계 절차입니다. 클라우드 리소스 생성·배포·요금 측정·부하 시험은 수행하지 않았습니다. 세부 한도와 비용은 도입 시 해당 지역·계정의 최신 설정을 다시 확인하세요.
