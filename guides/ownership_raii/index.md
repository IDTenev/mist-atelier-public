# 소유권·RAII · 자원 반환을 수명에 묶기

검토: 2026-09-20 · 분류: 구현 패턴 / 메모리·자원 수명 / 자원 관리 패턴

별칭: Ownership, RAII, Resource Handle, Reference Counting

적용 분야: C++ 메모리, 파일, mutex, 소켓, DMA 임대

## 개념과 특징

자원을 누가 닫을지 한 곳에 지정하고 소유자의 수명 종료 때 반환한다. C++ RAII는 객체의 생성·소멸에 자원 획득·반환을 연결한다. 참조 카운트는 공유 수명을 관리하는 별도 선택이며 데이터 경쟁을 없애지 않는다.

## 구조와 동작

획득 성공 → 소유 객체 → 빌려 쓰기/명시적 이동 → 마지막 사용 종료 → 정확히 한 번 반환

## 언제 쓰고 피할까

- 사용: 예외·조기 return·여러 실패 경로가 있어 수동 cleanup 누락이 생기기 쉬울 때.
- 비추천: shared_ptr를 모든 포인터에 붙여 소유 구조를 숨기는 방식. hard-real-time 경로에서 마지막 참조 해제 비용을 모르는 상태.

## 장점과 비용

- 장점: 정리 책임이 타입·scope에 드러나고 조기 반환에서도 cleanup이 유지된다. unique ownership은 공유 여부 판단을 단순하게 한다.
- 단점·비용: 순환 참조·비동기 작업 수명·파괴 순서를 설계해야 한다. 소멸자에 긴 대기나 실패 가능한 저장 작업을 넣으면 종료 지연이 불명확해진다.

## 설계·구현 가이드

1. 기본은 값 또는 unique ownership으로 두고 raw pointer/reference는 빌림임을 문서화한다.
2. 이동 후 이전 소유자는 비활성화한다. 외부 API handle에 전용 deleter 또는 RAII wrapper를 붙인다.
3. 공유 수명이 정말 필요할 때만 refcount를 쓰고 순환 관계는 weak reference 등으로 끊는다.
4. close/commit 실패를 알아야 하는 자원은 명시적 종료 API로 오류를 확인하고 소멸자는 안전한 최종 정리에 한정한다.

## 적용 예시

소켓을 연 뒤 mutex를 획득하고 전송 중 실패하더라도 lock_guard와 소켓 소유 객체가 각각 반환한다. 단, 송신 DMA가 포인터를 계속 사용한다면 함수 scope 종료만으로 버퍼를 반환해서는 안 된다.

이 절은 구현 결정을 설명하는 설계 사례다. 실행 프로그램이나 장비 설정 파일이 아니다.

## 실패·동시성·종료 조건

락 범위 안에서 외부 callback을 호출하면 재진입·교착이 생긴다. shared_ptr 자체의 수명 안전과 가리키는 객체의 thread safety를 혼동하지 않는다. 프로세스 강제 종료·전원 차단에서는 소멸 실행을 보장하지 않는다.

## 검증 기준

획득 단계별 실패·예외·조기 반환마다 leak/double-close가 없는지 확인한다. 비동기 완료 직전 소유자 종료와 참조 순환을 별도로 시험한다.
