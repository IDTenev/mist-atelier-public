SW 아키텍처 선택 지도: 이름보다 제약부터

문서 0.1.0 · 검토 2026-09-19 · 언어·제품 독립 설계 가이드

개념과 특징

아키텍처는 폴더 모양이 아니라 무엇을 함께 바꾸고, 누가 상태를 소유하며, 어디서 실패를 격리할지 정하는 규칙이다. 이 글의 추천은 조사 자료를 바탕으로 한 편집자의 판단이며 성능 순위나 제조사 인증이 아니다.

C4 원저자 설명 ↗은 시스템·컨테이너·컴포넌트·코드를 다른 확대 수준으로 다룬다. 여기서 컨테이너를 Docker와 동의어로 읽지 않는다. ADR 안내 ↗는 결정의 이유와 결과를 남기는 기록 방식이다. 둘은 실행 아키텍처가 아니라 설계를 설명하고 유지하는 도구다.

구조와 동작

다음 네 질문은 함께 답해야 한다. Hexagonal과 RTOS, 모듈러 모놀리스와 이벤트 처리는 동시에 사용할 수 있다.

축결정할 것후보
코드 구성변경·테스트 경계계층, 모듈러 모놀리스, Ports & Adapters, DDD
실행언제 누가 상태를 바꾸는가메인 루프, 상태 머신, RTOS, Actor
배포·데이터어느 실패가 어디까지 전파되는가단일 배포, Worker, 서비스 분리, 이벤트, 엣지
검증·운영선택이 계속 유효한가지연·자원 예산, 관측, 보안 경계, ADR

구현 순서

  1. 기능 목록보다 먼저 최악 응답 시간, 허용 데이터 손실, 오프라인 시간, RAM/저장 공간, 운영 인력을 적는다. 평균 처리량과 최악 지연은 분리한다.
  2. 입력부터 결과까지 한 가지 핵심 사용 사례를 그린다. 동기 호출·큐·저장·네트워크 화살표를 구별하고 각 상태에 소유자를 한 명 정한다.
  3. 같은 제약을 만족하는 가장 단순한 후보를 기준안으로 둔다. 추가 구조는 해결하는 구체적인 문제와 함께 제안한다.
  4. 정상·타임아웃·중복·재시작 시나리오를 동일 입력으로 실험한다. 비교 환경·측정 방법·실패 기준을 기록한다.
  5. 결과와 탈락 대안, 재검토 조건을 ADR 한 장으로 남긴다. 팀 규모나 제품명이 같다는 이유만으로 다른 프로젝트의 결론을 복사하지 않는다.

장점과 비용

축을 분리하면 같은 문제를 다른 수준의 패턴으로 비교하는 오류가 줄고 복합 구조를 설명하기 쉬워진다. 대신 결정 과정과 측정에 시간이 든다. 작은 일회성 스크립트에 모든 도표·문서를 강제하면 구현보다 관리가 커진다. 실제 변경과 위험이 있는 경계에만 적용한다.

검증과 전환

결정표에는 후보별 마감 충족 여부, 최대 큐 길이, 복구 시간, 배포/되돌리기 절차, 담당자를 적는다. 숫자 없는 별점 대신 관측 결과를 사용한다. 선택한 구조가 복잡해지면 가장 큰 병목 한 곳부터 분리하고 다시 측정한다. 설계 인수 가이드에서 체크리스트를 이어간다.

근거와 한계

위 출처는 2026-09-19 열람한 공식·원저자 웹 문서다. 이 안내는 선택 절차이며 모든 패턴의 전수 목록이 아니다. 표의 상황별 조합과 작업 순서는 독자적 제안이다. 특정 제품의 펌웨어·실기·부하 결과는 not_tested다. 표준 준수나 안전 인증을 대체하지 않는다.
