점진 파서 · 조각난 바이트에서 프레임 복원

검토: 2026-09-20 · 분류: 구현 패턴 / 통신·프로토콜 / 프로토콜 상태 패턴

별칭: Incremental Parser, Framing, Stream Parser, 프레이밍

적용 분야: UART, TCP, 파일 스트림, 센서 패킷

개념과 특징

한 번의 read가 메시지 하나라는 가정을 버리고, 입력 조각을 받을 때마다 파서 상태를 진행시킨다. TCP는 byte stream이며 send/read 경계가 메시지 경계와 일치하지 않는다. UART도 애플리케이션 프레임을 따로 정의해야 한다.

구조와 동작

헤더 탐색 → 고정 헤더 수집 → 길이 검증 → payload 수집 → 무결성 검증 → 전달/재동기화

언제 쓰고 피할까

  • 사용: 프레임이 여러 수신에 나뉘거나 여러 프레임이 한 번에 도착할 때.
  • 비추천: 상위 라이브러리가 이미 메시지 경계를 검증하는데 별도 파서를 중복 구현하는 경우. 자체 암호·인증 프로토콜 설계를 대신하지 않는다.

장점과 비용

  • 장점: 분할·병합된 수신을 같은 로직으로 처리하며 상태·메모리 한도를 명시할 수 있다.
  • 단점·비용: 잘못된 길이·동기 바이트·timeout·재동기화 정책이 복잡해진다. CRC는 우발 오류 검출이지 발신자 인증이 아니다.

설계·구현 가이드

  1. 길이 단위·엔디언·최대 payload·escape 규칙과 header 길이를 고정한다.
  2. 길이는 할당 전에 검사하고 header+payload 계산 overflow를 방지한다. 상태마다 최소 필요 바이트만 소비한다.
  3. 한 feed에서 여러 프레임을 처리하되 CPU 처리량 예산을 넘으면 다음 주기로 나눈다. 반환된 payload의 수명도 정한다.
  4. 부분 프레임 deadline과 stream 종료 시 오류를 정의한다. 손상 후 다음 sync를 찾을지 연결을 닫을지 프로토콜별로 선택한다.

적용 예시

[길이 2 byte][payload 최대 256 byte] 계약이면 0xFFFF 길이는 즉시 거절한다. payload 안의 헤더 같은 바이트를 매번 재탐색하면 정상 데이터가 잘리므로 현재 상태와 길이를 우선한다.

이 절은 구현 결정을 설명하는 설계 사례다. 실행 프로그램이나 장비 설정 파일이 아니다.

실패·동시성·종료 조건

바이트 유실 후 잘못된 프레임을 실행 명령으로 넘기지 않는다. 수신 ISR은 저장·알림만 맡기고 파서는 태스크에서 제한된 양을 처리한다. parser reset은 수신 버퍼와 함께 세대를 바꾼다.

검증 기준

동일 입력을 모든 단일 분할 위치로 나눠 결과가 같은지 검사한다. 1-byte 조각·연속 두 프레임·잘린 EOF·최대+1 길이·손상·timeout·fuzz 입력을 포함한다.

  • 링버퍼 · 순서를 지키는 유한 순환 저장소
  • UART 데이터가 끊겨 들어올 때 처리하기
