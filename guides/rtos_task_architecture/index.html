RTOS 태스크 구성: 우선순위보다 마감·소유권·예산부터

문서 0.1.0 · 검토 2026-09-19 · ESP-IDF 5.5.1 / Zephyr 3.7.0 비교

개념과 특징

태스크는 독립 실행 문맥이다. 모듈 수와 태스크 수를 같게 맞출 이유는 없다. 같은 주기와 자원을 공유하는 짧은 처리는 묶고, 독립 마감·장시간 대기·실패 격리가 필요한 처리는 분리한다. 아래 구성은 공통 설계 제안이며 SDK별 API를 섞어 쓰지 않는다.

ESP-IDF 5.5.1 FreeRTOS ↗는 SMP, 코어 affinity와 vanilla FreeRTOS와 다른 부분을 명시한다. 해당 IDF API의 태스크 스택 크기는 바이트 단위다. 타 SDK에 같은 단위를 가정하지 않는다.

구조와 동작

ISR: 원인 확인·최소 데이터 보존·통지
 ↓ bounded queue / notification
RX 소유 태스크 → 프레임 해석 → 제어 상태 소유자
                              ↓ 요청
                         버스 소유 태스크
낮은 긴급도: 로그·저장·원격 전송 (각각 제한된 자원)

Zephyr 3.7.0 message queue ↗는 고정 크기 항목을 복사한다. 포인터를 항목에 넣으면 포인터 값의 복사이지 대상 버퍼의 깊은 복사가 아니다. ISR의 대기 가능 여부와 전용 API 계약도 별도로 따른다.

구현 순서

  1. 각 작업의 주기/최소 도착 간격, 최대 실행·블로킹 시간, 마감, stack/heap, 코어, 호출 문맥을 표로 만든다.
  2. 우선순위를 긴급도와 측정된 마감으로 정한다. 한 태스크가 높은 우선순위로 계속 ready이면 낮은 태스크는 실행 기회를 잃을 수 있다.
  3. 공유 버스·버퍼·상태의 소유자를 정하고 복사/이동/반환 시점을 명시한다. 버스 소유권 참조.
  4. 큐 용량은 버스트, 최장 소비 중단, 메시지 크기를 근거로 정한다. 평균 생산량이 소비 능력을 계속 넘으면 큐를 늘리는 것으로 해결되지 않는다.
  5. stack high-water, queue peak, deadline miss, idle/CPU 여유를 관측하고 오류 경로를 포함해 시험한다. 코어 고정은 경쟁 조건의 해결책이 아니다.
  6. 종료 시 신규 입력 차단 → 진행 요청의 완료/취소 합의 → DMA/콜백 정지 → 자원 반환 순서를 설계한다.

장점과 비용

독립 대기와 우선순위 실행을 표현하기 쉽다. 대신 태스크별 스택·문맥 전환·경쟁 조건·우선순위 역전·교착 위험이 생긴다. mutex의 상속 정책과 중첩 제약은 커널별로 확인한다. ISR와 태스크가 공유하는 데이터를 volatile만으로 보호하지 않는다.

적용·비추천 조건

여러 통신·제어·저장 흐름이 독립적으로 기다리고 마감이 다른 장비에 적합하다. 충분히 짧고 예측 가능한 작업 몇 개뿐이라면 메인 루프가 단순할 수 있다. RAM이 적다고 태스크 스택을 임의로 줄이지 않는다.

Zephyr 3.7.0 workqueue ↗는 공용 스레드로 지연 작업을 처리하는 선택지다. 긴 블로킹 핸들러가 뒤 작업을 지연시키므로 긴 처리에는 별도 실행 경계가 필요할 수 있다. 모든 이벤트 횟수 보존이 필요한 입력을 하나의 재제출 work item으로 대체하지 않는다.

검증과 전환

동시 RX, 저장 지연, 큐 포화, mutex 경쟁, 종료 중 콜백, 코어 배치 변경을 시험한다. 한 기능부터 소유 태스크로 옮기고 이전 직접 접근 경로를 제거한다. 단일 코어의 단순 이용률 식을 SMP·ISR·블로킹이 섞인 시스템의 마감 보증으로 사용하지 않는다.

근거와 한계

고정 판본을 2026-09-19 확인한 설계 문서이며 완성 RTOS 프로젝트나 공통 API 예제는 아니다. 실제 stack 크기·priority·queue 길이는 대상에서 결정한다. MCU 빌드·실시간 응답·하드웨어 보호 검증은 not_tested다.
