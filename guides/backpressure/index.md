# 역압력 · 느린 소비자의 한계를 상류로 전달

검토: 2026-09-20 · 분류: 구현 패턴 / 통신·프로토콜 / 흐름 제어 패턴

별칭: Backpressure, Flow Control, High/Low Watermark, Credit

적용 분야: 스트림, 통신 게이트웨이, 파일 처리, 데이터 파이프라인

## 개념과 특징

하류가 더 받지 못할 때 상류의 생산·전송을 늦추는 피드백이다. 단순히 큐를 늘리는 것과 다르며, 상류를 멈출 수 없다면 손실·샘플링·저장 정책이 추가로 필요하다.

## 구조와 동작

하류 점유 증가 → pause/credit 감소 → 상류 감속 → 하류 배출 → resume/credit 회복

## 언제 쓰고 피할까

- 사용: 생산 속도를 조절할 수 있고 적체를 유한 메모리와 deadline 안에 묶어야 할 때.
- 비추천: 물리 센서가 멈출 수 없거나 제어 루프를 블로킹하면 위험한데 일률적으로 upstream을 기다리게 하는 경우.

## 장점과 비용

- 장점: 과부하가 메모리 폭주로 바뀌는 것을 줄이고 시스템의 실제 처리율로 흐름을 맞춘다.
- 단점·비용: 피드백 지연 동안 이미 날아오는 데이터가 있다. 고리형 대기나 공유 스레드를 막는 구현은 교착·기아를 만들 수 있다.

## 설계·구현 가이드

1. 바이트/항목/시간 단위를 통일하고 각 단계의 총 in-flight 상한을 적는다.
2. pause 상한 H와 resume 하한 L을 다르게 둬 흔들림을 줄인다. 전파 지연 동안의 입력 R×T만큼 여유를 남긴다.
3. Node Writable.write가 false면 이미 받은 chunk를 재전송하지 말고 추가 쓰기를 멈춘 뒤 drain 또는 error/close를 기다린다.
4. 멈출 수 없는 입력은 샘플링·drop·bounded spill 중 하나를 명시하고 제어 경로와 분리한다. 종료/실패 신호를 상·하류 모두에 전파한다.

## 적용 예시

100 KiB/s 입력에 pause가 반영되는 최장 시간이 20 ms면 약 2 KiB는 추가로 올 수 있다. 8 KiB 버퍼를 8 KiB에서 멈추도록 설정하면 늦다. 실제 burst와 전송 중 데이터까지 예산에 포함한다.

이 절은 구현 결정을 설명하는 설계 사례다. 실행 프로그램이나 장비 설정 파일이 아니다.

## 실패·동시성·종료 조건

highWaterMark는 일반적으로 절대 RAM 상한이 아니다. 한 chunk 크기, 내부 transform, 외부 대기 Promise까지 제한해야 한다. 하류 실패 후 drain만 기다리면 영원히 멈출 수 있다.

## 검증 기준

하류 지연·완전 정지·중간 오류를 주입하고 peak memory·in-flight·복구 후 순서를 측정한다. pause/resume 반복 시 busy loop와 알림 유실이 없어야 한다.
