# 워커 풀 · 동시 실행 수를 예산으로 관리

검토: 2026-09-20 · 분류: 구현 패턴 / 동시성·작업 분배 / 실행 자원 패턴

별칭: Worker Pool, Thread Pool, Work Queue, 작업 풀

적용 분야: 서버 계산, 이미지 처리, RTOS 지연 작업, 배치

## 개념과 특징

미리 정한 실행 주체가 유한 대기 큐에서 작업을 꺼낸다. 동시 실행 수 W와 대기 용량 Q는 서로 다른 예산이다. 한 스레드의 workqueue는 워커 여러 개가 병렬 실행하는 풀과 다르다.

## 구조와 동작

접수/거절 → 유한 큐 → W개 워커 → 결과·실패 회수 → 다음 작업

## 언제 쓰고 피할까

- 사용: 작업들이 독립적이고 스레드 생성 비용을 재사용할 수 있거나 CPU/외부 연결 수를 제한해야 할 때.
- 비추천: 단일 버스 접근처럼 결국 직렬인 작업, 아주 짧은 연산, 작업끼리 같은 풀의 하위 작업 완료를 기다리는 구조.

## 장점과 비용

- 장점: 스레드·스택·연결 수가 통제되고 생성 비용을 나눌 수 있다. 독립 CPU 작업은 병렬화 가능하다.
- 단점·비용: 공유 락·직렬 자원이 있으면 워커 증가가 경합만 키운다. 결과 순서와 취소, 장애 워커의 재시작을 설계해야 한다.

## 설계·구현 가이드

1. CPU-bound와 I/O-bound를 나누고 실제 처리량·지연·메모리로 W를 선택한다. Node worker_threads는 CPU 작업에 맞고 일반 비동기 I/O의 대체가 아니다.
2. Q와 접수 마감, 작업 ID, 결과 크기 제한을 둔다. 워커 수만 제한하고 무한 Promise 대기열을 만들지 않는다.
3. 긴 작업은 협력적 취소 지점과 최대 실행 시간을 둔다. RTOS workqueue에서 블로킹하면 뒤 작업 전체가 지연된다.
4. shutdown은 신규 거절→대기 작업 정책→실행 중 취소/완료→join 순서로 정의한다. 실패한 작업을 맹목적으로 자동 재실행하지 않는다.

## 적용 예시

워커 4개가 각자 같은 mutex 안에서 90% 시간을 쓰면 4배 성능은 기대할 수 없다. 큐 대기 p95, 실행 시간, 락 대기 비율을 분리해서 측정한 뒤 병렬화를 판단한다.

이 절은 구현 결정을 설명하는 설계 사례다. 실행 프로그램이나 장비 설정 파일이 아니다.

## 실패·동시성·종료 조건

워커가 동일 풀에 하위 작업을 넣고 기다리면 모든 워커가 대기하는 고갈 교착이 가능하다. 코어 고정은 측정 후 선택하고 태스크 우선순위·스택 최댓값·공유 메모리 소유권을 확인한다.

## 검증 기준

W+Q+1 접수 거절, 작업 throw, 워커 종료, 취소 응답, 결과 순서, 종료 deadline을 검사한다. peak active가 W를 넘지 않아야 한다.
