# Actor와 Supervision: 상태 소유와 재시작 경계를 함께 설계하기

문서 0.1.0 · 검토 2026-09-19 · 세션·장비 연결·백엔드 실행 구조

## 개념과 특징

Actor는 상태를 소유하고 메시지로 협력하는 실행 모델이다. 모든 Actor가 OS 스레드 하나를 갖는다는 뜻은 아니며 런타임마다 스케줄링·순서·메일박스 제약이 다르다. 한 상태 소유자를 두는 발상은 [Active Object](/guides/state_machine_active_object)와 비교할 수 있지만 두 구현의 보장 범위를 동일시하지 않는다.

[Erlang/OTP Supervisor 문서](https://www.erlang.org/doc/system/sup_princ.html)는 자식의 시작·종료·감시와 재시작 전략을 명시한다. one_for_one은 해당 자식, one_for_all은 묶음, rest_for_one은 시작 순서상 뒤 자식까지 재시작한다. 재시작 횟수/시간 창 한도는 영구 반복 장애의 확산을 막는 계약이다.

## 구조와 동작

```text
감독자
 ├─ 연결 Actor A: 연결 상태·요청 상관관계
 ├─ 연결 Actor B: 별도 상태
 └─ 저장 Actor: 영속화 계약
요청 → Actor mailbox → 상태 전이 → 응답/후속 메시지
실패 → 감독 정책 → 정리·복원 → 새 세대
```

재시작은 잃어버린 메시지·이미 수행된 외부 명령·영속 상태를 자동 복구하지 않는다. ‘프로세스가 살아남음’과 ‘업무가 한 번만 완료됨’을 별도 요구로 둔다.

## 구현 순서

1. 장치·세션·업무 단위 중 자연스러운 상태 소유자를 정한다. 상태 없는 짧은 함수까지 Actor로 바꾸지 않는다.
2. 메시지 타입·요청 ID·deadline·응답 대상·최대 크기·메일박스 상한을 정의한다.
3. 느린 I/O를 기다리는 동안 어떤 메시지를 처리할지 결정한다. 미완료 작업이 상태를 나중에 덮어쓰지 않게 세대를 확인한다.
4. 재시작 단위를 의존 관계에 맞게 묶고, 복원 가능 상태와 폐기할 캐시를 구분한다.
5. 감독 한도를 넘으면 상위 보고·서비스 중단·안전한 제한 모드 중 정책을 명시한다. 오류를 로그만 남기고 무한 재시작하지 않는다.

## 장점과 비용

공유 mutable 상태를 줄이고 세션별 장애를 격리하기 좋다. 반면 메시지 흐름 추적·타임아웃·메일박스 관리·프로세스 수명 비용이 생긴다. 메시지가 많거나 하나의 Actor에 요청이 집중되면 병목이 된다. 전역 일관성이 필요한 작업은 Actor만 도입한다고 해결되지 않는다.

## 적용·비추천 조건

독립 연결·장비·사용자 세션이 많고 일부 장애에서 복구해야 하는 시스템에 적합하다. 작은 MCU, 고정 주기의 짧은 계산, 강한 단일 트랜잭션이 중심인 로직에는 먼저 단순 루프·모듈을 검토한다. 하드웨어 제어는 재시작 후 출력 상태를 확인하는 절차가 필요하다.

## 검증과 전환

메일박스 포화, 응답 누락, 중복 요청, 종료 중 입력, 연속 crash, 감독자까지의 재시작 증폭을 시험한다. 한 장치 연결부터 분리하고 요청/응답 계약을 검사한다. [QP/C](https://www.state-machine.com/qpc/srs-qp_ao.html) 같은 임베디드 모델의 처리 문맥과 비교할 때 런타임 고유 특성을 따로 기록한다.

## 근거와 한계

공식 문서는 2026-09-19 열람했다. Erlang 링크는 열람 당시 OTP 29.1, QP/C는 변동 문서다. 위 연결 구성은 독자적 예시로 Erlang/장비에 실행한 결과가 아니다. mailbox 제한은 선택 런타임과 애플리케이션 계약으로 확인해야 하며 제품 실기 상태는 not_tested다.
