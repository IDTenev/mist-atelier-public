엣지·클라우드·오프라인: 연결이 없어도 지켜야 할 책임

문서 0.1.0 · 검토 2026-09-19 · 현장 장비·게이트웨이·원격 운영

개념과 특징

엣지는 현장에서 필요한 판단·처리를 하고 클라우드는 장기 분석·관리·배포를 맡는 역할 분리다. AWS IoT Greengrass 개요 ↗는 로컬 처리·필터·집계 같은 구현 사례를 설명한다. 제품을 선택하지 않아도 오프라인 책임·저장·재연결 계약부터 설계할 수 있다.

Azure IoT Edge 오프라인 안내 ↗는 연결 없이 동작하는 조건과 메시지 보관을 다룬다. ‘오프라인 지원’이 무한 저장, 영구 인증, 모든 기능의 무중단을 뜻하지 않는다. 장치 초기 설정·인증서·디스크·시간 정보도 확인해야 한다.

구조와 동작

센서/제어 MCU → 로컬 규칙·안전 경계
      ↓ telemetry
게이트웨이: 유한 spool · 압축/집계 · 재연결
      ↓ 인증된 전송 / 중복 판정
클라우드: 저장·분석·설정/업데이트 배포

현장 제어 마감과 안전 동작을 WAN 응답에 종속시키지 않는 것을 기준안으로 삼는다. 원격 명령은 대상·권한·만료·요청 ID·현재 상태 조건을 확인한다. 오래된 명령을 재연결 때 일괄 실행하지 않는다.

구현 순서

  1. 오프라인에서 반드시 유지할 기능, 멈춰야 할 기능, 허용 데이터 유실을 명시한다.
  2. 생성률 × 최대 단절 시간 × 항목 크기와 여유 공간으로 저장 예산을 잡는다. 디스크 포화 시 최신 상태/감사 기록의 우선순위를 구분한다.
  3. 저장 완료 확인과 서버 수신 확인을 구분하고 batch ID·장치 세대·순서·schema를 기록한다. 서버의 영속 중복 판정이 필요하다.
  4. 현장 시각과 수신 시각을 따로 보존한다. 시계가 되돌아가거나 정확하지 않은 구간을 품질 정보로 표시한다.
  5. 설정 충돌은 단순 최근 시각 승리로 처리하지 말고 권한·revision·승인 흐름을 정한다.
  6. 업데이트는 인증·무결성·전원 차단·부팅 성공 확인·복구 절차를 설계한다. MCUboot 설계 ↗는 이미지 검증과 교체의 구체적 참고이며 MCU마다 같은 flash 구성을 가정하지 않는다.

장점과 비용

연결 지연과 단절 영향을 줄이고 원시 데이터 전송량을 제한할 수 있다. 반면 장치별 배포·관측·보안·저장 수명·원격 복구가 필요하다. 버전이 다른 현장 장치와 서버가 오랫동안 공존할 수 있다.

적용·비추천 조건

공장·이동 장비·네트워크가 불안정한 센서와 현장 반응이 중요한 시스템에 적합하다. 데이터가 작고 연결 의존이 허용되는 단순 클라이언트는 로컬 인프라가 과할 수 있다. 보안 키를 임의로 공유하거나 인증 실패를 오프라인 모드라는 이유로 우회하지 않는다.

검증과 전환

장시간 단절, 전원 차단 중 쓰기, spool 포화, 시계 오차, 인증서 만료, 업데이트 도중 재부팅을 시험한다. 재연결 폭주가 서버를 압도하지 않게 전송량·재시도 예산을 둔다. 파이프라인, 장애 격리를 연결한다.

근거와 한계

2026-09-19 열람한 변동 제품 문서다. 공통 책임 분리는 독자적 설계안이며 위 제품 채택을 전제하지 않는다. 실제 장치 저장 수명·OTA·인증·WAN 장애·안전 시험은 not_tested다.
