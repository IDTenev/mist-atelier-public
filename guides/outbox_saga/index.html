Outbox·Saga: 여러 저장소의 변경과 실패를 연결하기

문서 0.1.0 · 검토 2026-09-19 · 서비스 통합·업무 복구 설계

개념과 특징

AWS Outbox 설명 ↗은 DB 변경과 발행할 메시지를 같은 로컬 트랜잭션에 기록하는 접근을 설명한다. 별도 전달자가 outbox를 읽어 발행한다. 전달자는 crash 후 같은 메시지를 다시 보낼 수 있으므로 소비자의 중복 처리가 여전히 필요하다.

AWS Saga orchestration ↗은 여러 로컬 트랜잭션을 조정하고 실패 시 보상 동작을 실행하는 방식을 다룬다. Saga는 분산 ACID 트랜잭션이나 완전한 rollback이 아니다. 보상 자체가 실패할 수도 있고 이미 외부에 보인 결과를 지울 수 없는 경우도 있다.

구조와 동작

로컬 transaction: 업무 변경 + outbox(event_id)
              ↓ commit
전달자 → broker → 소비자: 중복 검사 + 업무 반영

Saga: 단계 A 완료 → 단계 B 완료 → 단계 C 실패
      기록된 정책 → B 보상 → A 보상 → 최종/수동 복구 상태

Outbox는 변경 사실 전달, Saga는 여러 단계의 업무 진행 문제를 다룬다. 둘을 함께 사용할 수도 있다. 하나의 DB 트랜잭션으로 충분하다면 먼저 그것을 사용한다.

구현 순서

  1. 부분 완료가 무엇을 의미하는지 업무 담당자와 합의한다. 되돌릴 수 없는 동작은 별도로 표시한다.
  2. outbox에 고유 ID·업무 키·판본·생성 시각을 저장하고 업무 변경과 같은 commit에 포함한다.
  3. 발행 확인 후 처리 표시를 남긴다. 발행과 표시 사이 crash의 중복을 전제로 소비자를 설계한다.
  4. Saga 단계별 명령 ID, 성공 증거, timeout, 재시도, 보상, 수동 처리 기준을 영속 기록한다.
  5. 재시작 시 기록에서 이어가고, 오래된 단계 결과가 새 진행을 덮어쓰지 않도록 검증한다.
  6. 보상 실패는 별도 운영 상태로 노출한다. ‘보상 요청을 보냄’을 ‘복구 완료’로 보고하지 않는다.

장점과 비용

DB·메시지 사이 누락을 줄이고 부분 실패 흐름을 명시할 수 있다. 대신 전달 지연·중복·정리 작업·상태 저장·운영 복구 도구가 필요하다. orchestration은 중앙에서 순서를 추적하기 쉽지만 조정자의 가용성이 중요하다. choreography는 이벤트로 분산 협력하되 전체 흐름을 추적하기 어려울 수 있다.

적용·비추천 조건

독립 저장소를 가진 서비스의 예약·재고·승인 같은 다단계 처리에 적합하다. 한 DB로 처리 가능한 작은 업무를 굳이 분산시키는 근거는 아니다. 모터 이동·가열·실제 출고는 데이터 보상으로 물리적으로 원상복구되지 않을 수 있다. 그런 경우 안전한 중단·현장 확인을 별도로 설계한다.

검증과 전환

업무 commit 직후, 메시지 발행 직후, 소비자 반영 직후 각각 crash를 주입한다. 중복이 이중 부작용으로 이어지는지 확인한다. 동시에 진행하는 Saga의 충돌, 단계 timeout 후 늦은 성공, 보상 실패를 검사한다. 기존 흐름에서 가장 위험한 dual-write 한 곳부터 outbox로 교체한다.

근거와 한계

공식 웹 문서를 2026-09-19 확인했다. 예시는 개념 구현 순서이며 특정 DB·broker·조정 엔진의 실행 코드는 아니다. 저장소 원자성·장애 복구·실기 상태는 not_tested다. 이벤트 계약과 데이터 모델을 함께 검토한다.
